# 模块开发指南

本文档用于说明在 `nest-vue-admin` 中新增或改造一个业务模块时，应该如何按当前仓库规范落地。

## 适用范围

适用于以下场景：

- 新增一个后台业务模块
- 改造已有模块，并涉及后端、前端、权限点、字典表、测试或文档中的一项或多项

它不是环境安装指南，也不替代 [README.md](../README.md) 或 [CONTRIBUTING.md](../CONTRIBUTING.md)。如果你还没有完成本地环境准备，请先回到 `README.md`。

## 开发前检查

开始动手前，先确认下面这些问题：

- 是否已经存在相近模块可以复用，避免重复造轮子
- 是否需要新增表、字段、索引或调整 Prisma schema
- 是否需要新增菜单、按钮或接口权限点
- 是否需要新增字典类型或字典项，而不是直接写死枚举
- 是否会影响环境变量、部署说明、路线图或其他仓库文档

如果这些问题没有先想清楚，后面通常会出现返工：后端接口已经写完，才发现菜单和权限没设计；页面已经做完，才发现状态值不该硬编码。

## 后端模块开发

### 目录和命名

- 模块目录放在 `apps/server/src/modules/{module}/`
- 目录名使用 `kebab-case`
- 模块核心文件命名为 `{module}.module.ts`、`{module}.controller.ts`、`{module}.service.ts`
- DTO 文件优先使用 `req-{module}.dto.ts`

新增模块时，先看是否已有同类型模块可对照实现，保持目录和命名风格一致。

### Schema 与数据结构

- 如果业务字段或表结构发生变化，先修改 Prisma schema
- Schema 变更通过 Prisma migrate 管理，不要手工维护数据库结构
- Prisma 字段使用 camelCase，并补充 `/// 注释`

如果只是接口查询条件或页面展示变化，不一定需要改 schema；如果新增的是状态、分类、类型字段，先判断它是否应该进入字典表。

### Controller 与 Service 分层

- Controller 只负责路由分发和直接返回数据
- Service 承担所有业务逻辑
- 业务异常统一使用 `ApiException`

如果你发现 Controller 中开始出现大量判断、拼装、事务或缓存逻辑，说明职责已经越界，应该下沉回 Service。

### 分页、Swagger 与缓存

- 分页入参 DTO 继承 `PaginationDto`
- 分页返回格式保持 `{ list: T[], total: number }`
- Controller 只使用 `@ApiTags` 和 `@ApiOperation`
- DTO 字段使用 `@ApiProperty` 或 `@ApiPropertyOptional`
- Redis key 统一在 `common/constants/redisKey.constant.ts` 的 `REDIS_KEYS` 中定义，并通过 `generateRedisKey(...)` 生成带参数 key

如果模块没有缓存需求，不要为了“看起来完整”强行加 Redis 逻辑；只有在查询成本高、复用频率高或明确存在缓存诉求时再引入。

## 前端页面开发

### 页面目录与接口分层

- 页面目录放在 `apps/web/src/views/{module}/`
- 页面文件使用 camelCase，例如 `user.vue`
- 组件文件使用 PascalCase，例如 `UserDialog.vue`
- 模块业务接口放在 `apps/web/src/views/{module}/service.ts`
- `apps/web/src/api/auth.ts` 只保留登录、用户信息、路由、权限等全局接口

如果你在 `api/auth.ts` 中开始增加业务模块 CRUD，说明接口分层已经跑偏。

### 权限控制与状态使用

- 按钮、操作入口等前端权限控制使用 `v-auth="'sys:user:add'"`
- 与权限对应的接口能力要与后端权限点保持一致
- Pinia 状态在模板中优先通过 `storeToRefs` 解构后使用

如果只是纯展示页面、没有受限操作按钮，不一定需要新增按钮权限点；但只要出现新增、编辑、删除、导入、导出、审核等受控动作，就应评估权限点。

### 表单与样式规范

- 表单元素优先增加 `clearable`
- 下拉框优先增加 `filterable`
- `textarea` 优先显示字数统计
- 字符串输入长度应遵循 Prisma Model 中的长度定义
- 样式统一使用 CSS/SCSS 类控制，避免内联 style
- 对象操作优先使用扩展运算符或 `Object.assign`

这些规范看起来细，但它们决定了页面行为是否一致、是否便于维护。

## 权限点与菜单联动

新增模块时，不要只想到“接口能不能调通”，还要同时考虑菜单、按钮和接口权限是否成套落地。

判断方式可以按下面来：

- 如果只是页面样式调整或静态展示信息修正，通常不需要新增权限点
- 如果新增的是业务操作按钮，例如新增、编辑、删除、导入、导出、审核、启停，就应该新增对应权限点
- 如果新增后端受保护接口，就应该同步补 `@RequirePermissions(...)`
- 前端 `v-auth` 和后端 `@RequirePermissions(...)` 的权限标识应保持一致

菜单、按钮、接口权限的关系可以理解为：

- 菜单决定用户能否进入模块
- 按钮权限决定用户能否看到和触发具体操作
- 接口权限决定后端是否真正放行该能力

只做前端隐藏而不做后端权限保护，不算完整权限控制。

## 字典表使用规则

当字段表示状态、类型、分类、启用禁用、来源、等级等可配置业务枚举时，优先使用字典表，不要在前后端直接硬编码。

判断标准：

- 如果值可能被多个模块复用，优先使用字典表
- 如果值可能随着业务变化增加或调整，优先使用字典表
- 如果只是一次性、纯技术性的本地常量，才考虑留在代码中

常见处理方式：

- 已有字典类型能覆盖，只新增字典项
- 现有字典类型语义不匹配，再新增独立字典类型

无论前端还是后端，都不要各自维护一套内容相同但来源不同的业务枚举。

## 测试与提交流程

### TDD 顺序

按仓库当前约定推进：

1. Schema 定义
2. Red：先写失败测试
3. Green：最小实现通过测试
4. Refactor：整理结构并补充必要注释

### 最低测试要求

- 后端模块改动至少补对应的 Service 或 Controller 测试
- 如果改动涉及缓存、权限、认证、配置读取等关键链路，优先补回归测试
- 前端如果改动请求层、守卫、状态流或关键交互，也应补测试

不是每次都要补大而全的 e2e，但关键行为变化必须有可验证证据。

### 文档与路线图同步

如果本次改动涉及以下内容，也要同步更新文档：

- 开发流程或协作方式变化：更新 `CONTRIBUTING.md`
- 部署、环境变量、缓存或上传行为变化：更新相关部署文档
- 属于优化路线图中的任务：更新 `OPTIMIZATION_ROADMAP.md`

代码改完但文档不更新，长期看也是缺陷。

## 最小模块清单

提交前可以对照这份清单自查：

- [ ] 是否确认了 schema 是否需要变更
- [ ] 是否补齐了 DTO
- [ ] 是否实现了 Service
- [ ] 是否补齐了 Controller
- [ ] 是否完成了前端页面
- [ ] 是否补齐了模块 `service.ts`
- [ ] 是否评估并补齐了权限点
- [ ] 是否评估并使用了字典表
- [ ] 是否补了对应测试
- [ ] 是否同步更新了相关文档
