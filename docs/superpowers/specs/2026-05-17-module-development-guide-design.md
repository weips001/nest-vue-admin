# Module Development Guide Design

**日期**: 2026-05-17

## 背景

仓库已经补齐了 `README.md`、`CONTRIBUTING.md`、Issue 模板和 PR 模板，但对于“如何按当前仓库规范新增一个业务模块”仍缺少一份面向开发者的实战型文档。

目前相关规则散落在多个位置：

- `AGENTS.md` 中定义了目录、命名、RBAC、字典表、TDD、前端表单规范
- `CONTRIBUTING.md` 中定义了贡献流程、测试要求和提交约束
- `README.md` 中定义了本地启动方式

这些信息对熟悉仓库的人足够，但对新贡献者来说，不容易快速回答下面这些实际问题：

- 新增一个模块时后端目录和文件怎么组织
- 什么时候需要改 Prisma schema、DTO、Controller、Service
- 前端页面和 `service.ts` 应该怎么落位
- 什么时候必须新增权限点
- 什么时候必须用字典表，而不是硬编码枚举
- 至少应该补哪些测试和文档

## 目标

新增一份独立的模块开发指南，专门说明“新增或改造一个业务模块时，如何按仓库规范落地”。

具体目标：

1. 用一份文档串起后端模块、前端页面、权限点、字典表和测试要求
2. 让开发者能按开发顺序理解每一步要改哪些位置
3. 将“规则”与“判断标准”一起写清，而不是只做规范摘录
4. 更新 `OPTIMIZATION_ROADMAP.md`，记录该项已完成

## 非目标

本轮不处理以下内容：

- 不新增完整代码脚手架或示例模块
- 不把文档拆成后端篇、前端篇多份手册
- 不替代 `README.md` 的环境准备说明
- 不替代 `CONTRIBUTING.md` 的协作流程说明
- 不新增业务代码或自动化测试

## 方案对比

### 方案 A：规则汇总型

只把现有规范按主题重新整理到一份文档里。

优点：

- 写作成本低
- 维护负担小

缺点：

- 可执行性弱
- 开发者仍要自己判断实际开发顺序

### 方案 B：实战流程型（采用）

按“开发前检查 -> 后端模块 -> 前端页面 -> 权限点 -> 字典表 -> 测试与提交”的顺序组织文档。

优点：

- 更贴近真实开发流程
- 能把后端、前端、权限、字典、测试串起来
- 更适合新增业务模块时直接照着执行

缺点：

- 比单纯规则摘录更长

### 方案 C：完整教程型

以一个完整模块为样本，详细演示从零到一的所有文件改动。

优点：

- 最直观

缺点：

- 篇幅过长
- 后续维护成本高
- 容易因为示例过时而误导开发者

## 写法对比

### 写法 A：纯规范型

每章只写规则，不写决策标准。

缺点：

- 读者知道“应该这样”，但不知道“什么时候需要这样”

### 写法 B：规范 + 决策提示型（采用）

每章同时写清规则和判断提示，例如：

- 什么场景需要新增权限点
- 什么场景必须使用字典表
- 什么改动至少要补哪些测试

优点：

- 可执行性更强
- 篇幅仍可控

### 写法 C：小教程型

每章附完整模块示例。

缺点：

- 容易变成长教程
- 不符合本轮“短而实用”的目标

## 信息架构

文档路径：`docs/module-development.md`

建议章节如下：

1. 适用范围
2. 开发前检查
3. 后端模块开发
4. 前端页面开发
5. 权限点与菜单联动
6. 字典表使用规则
7. 测试与提交流程
8. 最小模块清单

## 章节设计

### 1. 适用范围

说明该文档面向以下场景：

- 新增后台业务模块
- 改造已有模块并涉及后端、前端、权限、字典、测试中的一项或多项

同时明确它不是环境安装指南，也不是通用贡献流程文档。

### 2. 开发前检查

需要回答的关键问题：

- 是否已有相近模块可复用
- 是否需要新增表或字段
- 是否需要新增权限点
- 是否需要新增字典表或字典项
- 是否需要同步文档、环境变量或部署说明

### 3. 后端模块开发

必须覆盖以下内容：

- 目录位置：`apps/server/src/modules/{module}/`
- 命名规范：kebab-case、`req-{module}.dto.ts`
- Schema 变更通过 Prisma migrate 管理
- Controller / Service 分层
- 分页 DTO 继承 `PaginationDto`
- Swagger 注解使用范围
- 业务异常使用 `ApiException`
- Redis key 统一在常量中定义

### 4. 前端页面开发

必须覆盖以下内容：

- 页面目录：`apps/web/src/views/{module}/`
- `service.ts` 负责业务 CRUD 接口
- `api/auth.ts` 只保留登录、用户、路由、权限等全局接口
- 页面和组件命名规则
- `v-auth` 权限控制方式
- 表单 `clearable`、`filterable`、`textarea` 字数、字符串长度限制
- `storeToRefs`、样式类控制、对象扩展操作规范

### 5. 权限点与菜单联动

必须解释以下判断标准：

- 什么时候只改页面，不需要新增权限点
- 什么时候需要新增按钮权限点
- 什么时候需要同步后端 `@RequirePermissions(...)`
- 菜单、按钮、接口权限之间的联动关系

### 6. 字典表使用规则

必须解释以下判断标准：

- 状态、类型、分类、启用禁用等字段优先使用字典表
- 前后端都不应直接硬编码业务枚举值
- 什么时候只新增字典项，什么时候需要新增独立字典类型

### 7. 测试与提交流程

必须覆盖以下内容：

- 遵循 Schema -> Red -> Green -> Refactor 的 TDD 顺序
- 后端模块改动至少补对应 Service 或 Controller 测试
- 前端请求链路、守卫、状态流或关键交互改动要补回归测试
- 如果涉及路线图项，应同步更新 `OPTIMIZATION_ROADMAP.md`
- 如果涉及协作规则或部署行为，也要同步相关文档

### 8. 最小模块清单

文末提供一个短 checklist，帮助开发者自查：

- Schema
- DTO
- Service
- Controller
- 前端页面
- `service.ts`
- 权限点
- 字典表
- 测试
- 文档

## 文案风格

- 全文使用中文
- 用短段落、checklist 和少量路径示例组织内容
- 不提供大段示例代码
- 强调“怎么判断”和“要改哪里”，而不是泛泛重复原则

## 实施范围

预计新增或修改文件：

- 新增 `docs/module-development.md`
- 更新 `OPTIMIZATION_ROADMAP.md`

## 验证策略

本轮属于文档治理任务，不需要执行业务测试。验证重点如下：

1. `docs/module-development.md` 文件存在且结构完整
2. 文档内容与 `AGENTS.md`、`CONTRIBUTING.md`、`README.md` 中现有规则一致
3. 路线图中“增加模块开发指南”状态更新为 `已完成`
4. 修复记录追加本轮文档治理说明

## 风险与取舍

- 风险：文档如果只是规则摘录，可执行性不足
- 风险：文档如果写成完整教程，后续维护成本过高
- 取舍：采用“实战流程型 + 规范/决策提示型”，在可执行性和维护成本之间取平衡

## 成功标准

- 新贡献者能快速判断新增模块要改哪些目录和文件
- 开发者能明确知道何时新增权限点、何时使用字典表
- 开发者能按仓库约定补测试和更新相关文档
- `OPTIMIZATION_ROADMAP.md` 中该项完成并留有记录
